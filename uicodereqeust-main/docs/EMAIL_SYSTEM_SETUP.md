# Production email configuration

## Application sender

All application emails sent through Brevo use the fixed production sender:

```text
Ronsberger HMO <noreply@ronsbergerhmo.io>
```

The Edge Functions set this sender in each Brevo API request. They do not rely on `BREVO_FROM_EMAIL`; a stale value or Brevo account default cannot change the application's From address. The sender domain must remain verified and enabled for transactional email in Brevo.

The **Test Invite** row shown in the Brevo dashboard is a dashboard-generated test message. Its shared `brevosend.com` sender does not exercise the application's invitation function and is not evidence of the app's From address. Check an event generated by **Users → Invite User** or **Resend Invite** to verify the application path.

## Edge Function configuration

Configure these server-side values in the self-hosted Supabase Edge Functions environment managed through Coolify:

| Variable | Requirement |
| --- | --- |
| `BREVO_API_KEY` | Required; a transactional email API key. Keep it server-side and never include it in a `VITE_*` variable or logs. |
| `SUPABASE_URL` | Required; `https://api.ronsbergerhmo.io`. |
| `SUPABASE_SERVICE_ROLE_KEY` | Required for Edge Function server-side admin operations; keep it private. |
| `SITE_URL` | Set to `https://app.ronsbergerhmo.io`; invitation links are pinned to the production registration page. |

`BREVO_FROM_EMAIL` is no longer read by application email functions. Remove it from the Edge Function environment if it contains an old or shared sender; no API key rotation is required solely for that variable.

## Invitation behavior

- New users receive a Supabase Auth invite link, delivered through Brevo with the production sender.
- Resending preserves the existing pending Auth user and creates a fresh magic link; it does not delete or recreate the account.
- Completed accounts are not silently re-invited. Use account-management controls for those records.
- The registration redirect is `https://app.ronsbergerhmo.io/register` and the seven-day token lifetime is configured in the self-hosted GoTrue service.
- The invitation endpoint reports success only when Brevo returns HTTP 201 with a message ID. That means **accepted by Brevo**, not guaranteed inbox delivery. Confirm `Delivered`, `Blocked`, or `Bounced` in Brevo transactional logs.
- Rejections return an error to the admin and are not displayed as a successful send.

## Safe delivery verification

1. Use an administrator-controlled test mailbox; do not send tests to staff or patients without authorization.
2. From the production portal, create an invitation for that test identity and confirm the function response says Brevo accepted it.
3. In Brevo transactional logs, confirm the message recipient, `noreply@ronsbergerhmo.io` sender, and final delivery event.
4. Use **Resend Invite** on the same pending account and confirm a second accepted/delivered event without a duplicate Auth identity.
5. Open the link and confirm it returns to `https://app.ronsbergerhmo.io/register` and allows the pending user to complete setup.

Do not paste API keys, service-role credentials, action links, or invitation tokens into logs, tickets, or chat.
